Client specification:

We will need to create a real client with Web based interface that will allow to run requests to ai_agent_server (like simple_client does).
The real device will be based on Rapberry Pi with 1024x768 touch screen.
Interface should allow to initiate requests without parameters (current state, battery status) and parameterized requests (for last xxx hours, from date to date).
Also need to made possibility to switch On/Off additional audio and/or graph (it will be used with requests that support it).
When we got initial 200 OK from server that reqiest received for processing need to how message "Thinking..." and probably time counter (not necessary).
We should not allow to initiate another request untill the current will noi be finished.

If there are text only (voice Off, graph Off) - Just put returned text on the screen.
If there are also voice file returned in the answer also download and play this file using current system audio output.
If there are also graph file returned in the answer also download and show this file on screen Planned resolution is 800x600 but it can be changes if needed.

Response format:
Server responds with JSON. Audio and/or graph, when present, are returned as URLs within that JSON (not inline binary data) — the client downloads them separately before playing/displaying.
These URLs are served by ai_agent_server itself (no separate file host). Audio files are WAV; graph files are PNG.

Error and timeout handling:
- If the server returns a non-200 status, or a connection error/timeout occurs while waiting for the response, the client must show a visible error state (not remain stuck on "Thinking...") and unlock the UI so a new request can be initiated.
- The client enforces its own timeout on a pending request (in addition to whatever the server-side processing time is), so a hung server call cannot lock the touchscreen indefinitely.
- The "Thinking..." state includes an elapsed time counter (promoted from optional to required), giving the user a visual cue for how long a request has been pending and a basis for the client-side timeout.

UI layout (1024x768 touchscreen):

The screen is split into a fixed header, a left sidebar, and a main content area.

Header (1024x60, top): shows the interface title on the left and a status readout on the right ("Ready" when idle).

Left sidebar (224 wide, full height below header):
- Requests section: two always-visible buttons for parameterless requests, "Current state" and "Battery status".
- Time range section: a "Last hours" button paired with a combo box offering 1-48 hours in 1-hour increments (default 12); a "Run range query" button; a "From date" picker (default: 7 days ago) and a "To date" picker (default: today), placed below the button.
- Output section: "Audio" and "Graph" as on/off toggle switches (not buttons), so state is visible at a glance without reading text.
- Answer text section: a label ("Answer text") that also functions as the processing-status indicator — shows "Thinking... m:ss" with an elapsed timer while a request is pending, and reverts to idle once a response arrives. This is a label/status only; the actual answer content is not shown here.

Main content area (800 wide, right of sidebar):
- Graph area (800x600, top): displays the returned graph image (PNG) when the Graph toggle is on and the response includes one.
  - When Audio is on and Graph is off (or the response has no graph): this area instead shows a simple looping animation (e.g. equalizer bars) indicating audio is playing. The animation is not audio-reactive — it loops on its own timer, purely as a "something is playing" indicator.
  - When both Audio and Graph are off (text-only response): this area is hidden entirely, and the answer text strip below expands to fill the freed space.
- Answer text strip (800x108 normally, expanded when the graph area is hidden): displays the full text of the response.

Behavioral notes:
- Only one request may be in flight at a time; all request-initiating controls are disabled while "Thinking..." is active.
